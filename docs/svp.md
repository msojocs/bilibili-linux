# SVP frame interpolation

The optional frame interpolation integration uses the Bilibili DASH playback URL and renders SVPFlow output back into the normal Bilibili player surface. The original video element is hidden only after the encoded stream can play, so the normal player remains usable when the feature is disabled or unavailable.

## Requirements

- `mpv` with VapourSynth support
- `vapoursynth`
- SVPFlow (`svp-bin` installs it under `/opt/svp` on Linux; SVP 4 installs it under `Program Files` on Windows)

Open the extension settings under `Playback`, enable frame interpolation, and enter the desired output FPS from 30 through 600. The same target FPS is available next to the quality control. Existing multiplier settings are migrated to an equivalent FPS value once. Non-default SVP and mpv installations can be selected with the native path pickers in the same settings page. The main process validates and persists these paths; the player renderer cannot supply executable paths when starting interpolation.

The optional per-format target matrix distinguishes the source representation by both resolution and cadence: 4K, 1080p, 720p, 480p, and 360p, each with 30 FPS (up to 45), 60 FPS (46-90), and 120 FPS (above 90) source classes. A value of zero disables interpolation for that class; unknown intermediate resolutions and missing frame-rate metadata retain the fixed target. The bundled defaults map 4K30 to 60 FPS, disable interpolation for 4K60 and 4K120, and map the remaining classes to 120 FPS. Each matrix cell can benchmark the exact matching representation from the currently open video when that representation exists; absent 60 or 120 FPS representations are reported as unavailable rather than inferred from another stream. The benchmark uses Bilibili's real quality control to switch the player, seeks to zero, and runs the normal interpolation playback path with the current engine, decoder, queue, transport, renderer, and encoder settings. It starts at the active display refresh rate, up to the 600 FPS setting limit, and tests descending target values until production and presentation throughput settle without persistent stalls or unexpected drops. Filter initialization is excluded from every stable sampling window. The previous quality, position, speed, pause state, and interpolation intent are restored afterward, and the result remains in the settings draft until the user saves it.

The integration verifies that the selected mpv actually lists the `vapoursynth` video filter before starting. Installing the VapourSynth library alone is not sufficient when mpv was built without that filter. On Arch Linux, the current repository `mpv` package may omit it; `mpv-full` from AUR is one known full-featured alternative. The settings page reports the effective mpv path and rejects incompatible builds instead of misreporting the final encoder fallback as failed.

The engine selector exposes the methods actually available in the local SVP installation. SVPFlow is available with the base SVPFlow plugins. NVIDIA Optical Flow uses `SmoothFps_NVOF` and is offered on NVIDIA systems. RIFE is offered only when the optional HolyWu RIFE VapourSynth plugin and at least one model are installed. Its API accepts built-in model IDs 0 through 9, but only model directories containing both `flownet.bin` and `flownet.param` are listed. Custom models under the plugin's `models` directory are also detected and passed through the trusted main-process model-path map; the renderer cannot supply an arbitrary path. Older invalid model 23 settings are migrated to Auto, which prefers installed RIFE v4. The base `svp-bin` package does not include this plugin or its models. SVPFlow and NVIDIA Optical Flow share SVP's rendering shader, artifact mask, scene mode, and scene-change controls, matching the parameters produced by SVP Manager. A finer NVOF grid improves motion boundaries at additional GPU cost. SVPFlow OpenCL devices are listed with their SVP `gpuID`; explicit choices are preserved, while Auto prefers a device matching an explicitly selected decoder or encoder vendor. The advanced settings expose the stable controls for the selected engine. Values are validated before being written to the generated VapourSynth script. Selecting SVPFlow GPU is explicit: a missing OpenCL device or GPU initialization failure is reported instead of silently switching to CPU.

SVPFlow's GPU queue count maps directly to `SmoothFps`'s `gpu_qn`: it controls the number of concurrent OpenCL rendering requests used to hide GPU latency. It is not a GPU utilization target or a processor-count setting. The preceding `svp1.Analyse` motion-vector stage remains CPU and memory-bandwidth intensive, so a low aggregate GPU percentage does not imply that increasing `gpu_qn` will make a CPU-bound 4K profile faster.

Playback speed changes the interpolation pipeline rate so that its displayed rate remains capped by the selected target. SVPFlow scene mode 2 only accepts output rates of at least twice the source rate, while mode 1 requires an output rate no lower than the source. The generated script therefore applies a runtime-only compatible scene mode when increased speed crosses either boundary; the stored user setting is left unchanged and is restored automatically when the rate permits it. Debug OSD shows both values when this happens.

Linux loads `plugins/libsvpflow*.so`. Windows loads the 64-bit VapourSynth plugins from `plugins64/svpflow*_vs64.dll`. The integration detects `/opt/svp` on Linux and the standard SVP 4 locations under `Program Files` on Windows, including its bundled `mpv.exe`. Non-standard installations can be selected with the process environment variables `SVP_HOME` and `SVP_MPV_PATH`; executable and plugin paths are never accepted from the remote renderer.

The transport selector defaults to `Auto`. On Linux it tries the optional POSIX shared-memory ring first, then localhost raw frames, and finally the H.264 compatibility stream. Other platforms start with raw frames because the Linux native module is not packaged there. Chromium draws fixed-size 8-bit or 10-bit I420 frames in the normal Bilibili player surface, so the lossless routes have neither output encoding nor a second browser video decode. Their queues are byte-bounded and apply backpressure instead of retaining an unbounded uncompressed buffer. Explicit `Shared memory`, `Raw`, and `H.264` selections never silently switch transport. `H.264` always uses a low-latency fragmented MP4 stream and rejects 10-bit input rather than reducing bit depth.

The settings list the source decoders and output encoders reported by the selected mpv build, including NVIDIA NVENC, Intel QSV, AMD AMF, Linux VA-API render devices, and software x264 where available. Detection only populates this list and annotates locally suitable entries with `（推荐）`; it never changes a saved explicit selection. An explicitly selected source decoder or encoder either starts successfully or reports an error. Only the user-selected `Auto` modes permit software or cross-backend compatibility fallback. The output video stays below Bilibili's danmaku DOM while the original element remains the audio and control clock. The original element is removed from composition while interpolation is active. No extra mpv window is created.

The playback settings provide encoder speed/quality preference and prebuffer controls. `p1` is the lowest-overhead preference; it is translated to the nearest equivalent supported by the selected backend. A lower quality number produces a higher-quality, larger local stream. The prebuffer value is measured in wall-clock playback seconds, so 4 seconds at 3x speed reserves roughly 12 media seconds. The encoder runs ahead of playback and is paused between configurable low/high watermarks instead of being permanently throttled to 1x.

mpv is configured with the Python VSScript library reported by `vapoursynth get-vsscript`. mpv hardware decoding remains independently configurable from the interpolation engine and output encoder. Enable `Debug` in Playback settings to write a per-session mpv log. The color OSD separates decode throughput from actual presentation FPS and shows the selected decode and encode backends in the complete source -> interpolation -> encoder -> buffer -> Chromium -> display path. Pipeline throughput and the measured shared-memory write, read, assembly, and upload durations use a rolling 0.5-second active-work window. The mpv pipeline value is an end-to-end decode/interpolate/output period because SVPFlow does not expose a portable per-frame kernel timer; it is deliberately separate from the measured shared-memory copy time. Buffer watermarks, stalls, dropped frames, A/V error, system/mpv/renderer CPU, RAM, and available GPU metrics are shown alongside it.

The worker preloads the system Python/VSScript dependencies. The source decoder control only exposes copy-back hardware modes because VapourSynth/SVPFlow consumes system-memory frames. `Auto` uses mpv's `auto-copy-safe` selection and may fall back to software; explicit modes disable that fallback. An OpenCL device is required when SVPFlow GPU mode is selected.

The integration always processes the selected source resolution and lets Chromium scale it for display. It does not impose a resolution cap.

For DASH playback, the integration selects the video representation whose ID matches the response's active `quality` value and prefers AVC when multiple codecs represent the same quality. It does not assume that the first DASH entry is the active quality. Request sequence, quality, URL path, duration, and source dimensions guard switching; late responses from older play-url requests are ignored. When the video, episode, or quality changes while interpolation is active, the old process is stopped and the selected stream is restarted automatically, and the encoded dimensions are checked before the original picture is hidden. Shared-memory seeks reuse the existing mpv/VapourSynth graph by flushing the ring and rebasing its absolute frame sequence. Playback-rate changes reuse the graph when its media output FPS is unchanged; other rate changes rebuild it because that FPS is part of the VapourSynth script. The source video continues playing during a rebuild, and a per-profile startup estimate moves the new graph's start point forward to meet the live playback clock instead of warming obsolete frames. If shared-memory output falls behind, the player temporarily shows the source video and seeks the existing graph to a predicted future takeover point. It waits for that seek's first frame, learns the actual pipeline latency, and requires a small reserve before showing interpolation again. This drops stale SVP work without pausing audio or silently reducing the configured FPS; an impossible target remains visible in the OSD while the source picture stays usable.

The raw transports remove codec loss but are not end-to-end zero-copy: VapourSynth requires copy-back frames, shared memory still performs one reusable-buffer read, and Chromium uploads the YUV planes for composition. The OSD reports pipeline throughput, measured shared-memory write/read, frame assembly, GPU upload, queue, backpressure and presentation time as milliseconds and percentages of the target frame budget. It also reports per-process CPU, GPU engines, memory, dropped/skipped frames and A/V drift. H.264 transport keeps the cross-process payload compressed and lets Chromium handle scaling and composition. On Linux, the Chromium output decoder can be left on `Auto`, pinned to a detected DRM render node, or disabled in favor of software decode. Device choices take effect after an application restart; detection only marks a recommendation and never switches the configured device during playback. A changed device is committed only after the main window loads and remains stable. If its GPU or renderer process fails, the application restores the previous known-good setting and relaunches; an interrupted trial is restored on the next launch. `--svp-chromium-safe-mode` or `BILIBILI_SVP_CHROMIUM_SAFE_MODE=1` disables GPU acceleration for one rescue launch without overwriting the saved selection. Startup enables the applicable accelerated Linux video-decode and zero-copy features for the selected device. Explicit `disable-gpu` and `disable-accelerated-video-decode` flags are respected, no sandbox is disabled, and Chromium may still reject a stream the installed driver cannot decode. Windows exposes Chromium's platform default or software decode while retaining explicit mpv source-decoder and output-encoder choices.

## Source layout

SVP code is kept outside the decompiled Bilibili implementation. `src/inject/common/electron-tool.ts` contains only four integration calls; runtime discovery, capability probing, script generation, settings IPC, metrics and pipeline control live under `src/inject/svp/`. Player transport, rendering, stream selection, OSD formatting and startup fallback live under `src/extension/ui/player/svp/`. The settings page is a coordinator whose tab panels live under `src/extension/ui/setting/svp/`. The preload exposes five narrow shared-memory methods while its native loader and WebGL renderer remain in `res/scripts/svp-shm-bridge.js`. This keeps upstream-facing files as stable adapters and makes the optional Linux native transport removable without changing Bilibili business code.

The feature is built and packaged through the repository's normal `pnpm run build` and platform packaging commands. It does not require a separate launcher or AppImage patch step.
